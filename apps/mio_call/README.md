# Mio Call — 第1段（ズーム対談スタイル）

公開先: https://claude.ai/code/artifact/d217648b-1661-4305-a6cf-10bc7569f79b

澪と声で会話する。バストアップ正面の1枚を顔として使い、口だけを動かす。

## なぜこの構成か

「コストフリーで GPT-Live 相当の音声会話」という条件に対して、
追加のAPI契約が要る部品を1つも使わない構成にした。

| 役 | 使うもの | 追加費用 |
|---|---|---|
| 耳 | 端末の音声認識（`webkitSpeechRecognition`, ja-JP） | なし。iOS/Safari に内蔵 |
| 頭脳 | Artifact の `sample` 機能から Claude を呼ぶ | なし。閲覧者自身の Claude 使用量を使う |
| 声 | 端末の読み上げ（`speechSynthesis`, ja-JP） | なし。iOS/Safari に内蔵 |
| 顔 | 参照シートのバストアップ正面（端末内に保存） | なし |

OpenAI Realtime API を使う道は、月額でも従量でも必ず課金が発生する。
第1段では会話が成立するかどうかを確かめたいだけなので、課金のある部品を外した。
Realtime API に移るのは、この構成で会話が成立してから判断すればよい。

なお `sample` は Ken さんの Claude 使用量を消費する。無料なのは「別途の請求が増えない」
という意味であって、消費量がゼロという意味ではない。

## 口の動かし方

音量ではなく**読みがな**で動かしている。

返事は JSON で受け取る:

```json
{"reply": "話す文", "kana": "よみがな", "emotion": "happy"}
```

`kana` を5母音（あいうえお）＋ん＋閉じ、の7つの口の形に変換して順に出す。
日本語は1拍1母音なので、これで形が合う。漢字の読みはブラウザでは分からないため、
返事と一緒に読みを返させている。

- 小さい「ゃゅょ」と小書き母音は前の拍に乗る（「きょう」は2拍で「お・う」）
- 長音「ー」は直前の母音を保つ
- 「っ」と句読点は口を閉じる

開くのは 45ms、閉じるのは 85ms の非対称で補間する。設計書の `lipsync.py` と同じ考え方。

話す速さは端末の声によって違うので、1回話すごとに実測して次回に反映する（初期値 7.4拍/秒）。

## 顔の差し替えと口の位置

### 表情は「組み合わせ表」であって「絵の一覧」ではない

感情6 × 強さ3 × 視線5 × 涙2 を絵で持つと 180 枚になり、全部を同じ顔に保つことが
そもそも不可能になる。掛け算になるのは「顔まるごと」を持つからで、**層で持てば足し算**になる。

| | 掛け算（顔ごと） | 足し算（層ごと） |
|---|---|---|
| 感情6・強さ3・涙2 | 36枚 | **7枚** |
| 視線5 を足す | 180枚 | 7枚（+視線は将来コードで） |

いま持つ枠は8つ。

- **通常** — これだけで会話できる
- **目**：閉じた目 / 笑う目 / 見開く目 / 潤んだ目
- **眉**：上げ眉 / 困り眉 / 怒り眉

各画像は顔全体で作ってよい。使うのは目の帯・眉の帯だけで、切り出しは自動。

- **強さ**は絵ではなく**重ねる濃さ**で出す。弱い笑顔＝笑う目を45%で重ねる。
- **涙**は絵ではなく**コードで描く**。静止画では「潤んでいる」までしか出せず、
  流れる涙は描いて動かすしかない。潤んだ目の絵に、流れる筋と粒を重ねる。
- **まばたき**は閉じた目の枠へのクロスフェード（閉じ70ms・保持50ms・開き100ms）。
- 目と眉は別々に補間する。眉が先に決まって目が後から届いてよい。
  同じ帯で絵を入れ替えるときは一度0まで薄くするので、2つの目が同時に出ることはない。

### 帯の位置

「目の位置を合わせる」で左目・右目の中心をタップすると、両目の間隔を基準に帯を決める。

- 眉の帯：目の中心の 0.82〜0.26 間隔ぶん上
- 目の帯：0.26 上 〜 0.32 下

眉は目の中心の 0.3〜0.45 間隔ぶん上にあるので、この範囲に入る。
2つの帯は重ねない。重ねると、上に来た層が下の層の特徴を塗り戻してしまう。

読み込んだ画像は 640px に縮小して端末内（`localStorage`）に保存する。どこにも送信しない。
端末ごとの保存なので、iPhone と Mac では別々に選ぶ。

### 口の大きさと「隠す範囲」は別

この2つを1つの数値で兼ねていたため、口を小さくすると元の絵の口がはみ出していた。いまは別。

- **口の大きさ** — 描く口の寸法
- **隠す範囲** — 元の絵の口を覆うパッチの半径

「口の位置を合わせる」で口の中心をタップすると、**隠す範囲は自動で測る**。
中心のまわりで、周囲の肌より明らかに暗い画素（＝唇の線）を集め、
中心からの距離の94パーセンタイルを取り、1.65倍する。
パッチは半径の74%までは完全に不透明なので、測った端は必ず不透明な内側に入る。
外れたときはスライダーで直せる。

## 分かっている制約

- 画面ロックやアプリ切替で音声認識も読み上げも止まる（iOS の仕様）。切り替え時に明示的に停止している。
- 読み上げ中は聞き取りを止める。自分の声を拾ってしまうため。
- `emotion` は受け取って記録しているが、まだ表情の切り替えには使っていない。
  表情ごとの画像が揃った時点で、ここに繋ぐ。
- 音声認識が使えない端末では、文字入力欄から送れる。

## 実物での検証結果（2026-09-07）

澪のバストアップ2枚（目を開いた通常／目を閉じた絵）を実際に通した記録。

| 工程 | 結果 |
|---|---|
| 2枚の位置合わせ | 倍率 1.00・残差 4.1（同じ構図） / 34ms |
| 目の位置の自動検出 | 検出成功。間隔は画像幅の23.4% |
| 口の測定 | 半幅37px・高さ19px → 口の大きさ93px・隠す範囲59px（画像幅の9.2%） |
| まばたき | 12秒で1コマ6段階の急変を検出。動いている |

`mouth_on_mio.png` が彼女の顔に実際に描いた口（閉じ／あ／い／お）、
`blink_on_mio.png` がまばたきの途中のコマ。

### ここで見つかった不具合

- **`fitCanvas` が未定義**。直前の変更で定義ごと消していた。起動時に例外が出て、
  アニメーションの開始と Claude への接続がまとめて止まっていた。
  以後、起動時の例外は画面の記録に出る。
- **口の測定が髪を拾っていた**。基準の暗さを「窓の中で一番暗い画素」から取っていたため、
  ほぼ黒の髪が窓に入ると基準がそちらに引きずられ、唇より暗いものしか拾わなくなっていた。
  タップした場所そのものの暗さを基準にするよう変更。
- **測り方が範囲の百分位だった**。鼻の影や髪など、口とつながっていない暗い部分まで
  口の一部として数えていた。タップ地点から暗い連なりを外へ辿る方式に変更。
- **描く口の大きさが実物と合っていなかった**。元の口を隠すだけになり、口が消えていた。
  測った半幅から自動で決めるようにした。

## 澪の顔はページに入っている

通常と閉じた目の2枚は、560px の JPEG としてページに埋め込んである（各72KB）。
読み込む操作も位置合わせも要らず、開けばその顔で話す。まばたきもする。

測ってある値も一緒に入れてある（口の中心 0.505 / 0.4296、口の大きさ93px、隠す範囲59px）。
端末に前の設定が残っていても、自分の絵を入れていなければ内蔵の値で上書きする。
前の絵はもう無いのだから、それに合わせた設定を残しても意味がないため。
自分で調整したあとは `mio.calFor=builtin` の印が付き、以後は調整のほうを残す。

枠を押せば別の絵に差し替えられる。「最初の顔に戻す」で内蔵の顔に戻る。

## 絵とコードの分担

絵でしか出せないものと、コードでしか出せないものがある。混ぜると両方とも下手になる。

| 絵（Gemini）でしか出せない | コードでしか出せない |
|---|---|
| まぶたの形（閉じる・笑う・見開く） | 強さの中間（重ねる濃さで連続的に変わる） |
| 眉の形と角度 | 動き（到着時の反動・呼吸・話すときの頭の揺れ） |
| 潤んだ瞳 | 流れるもの（涙の筋と粒） |
| — | 組み合わせ（どの眉 × どの目 × どの強さでも作れる） |

### 眉をコードで動かさない理由

眉の帯を上下にずらす方式は試さなかった。ずらす前に元の眉を消す必要があり、
消すには肌色で塗るしかない。ところが澪は**前髪が眉の高さまで下りている**ので、
塗った瞬間に前髪が消える。この絵に対しては成立しない。
だから眉だけは絵で持つ。

## 絵を足さずに動いているもの

`expressions_no_new_art.png` が、通常と閉じた目の2枚だけで作った6表情。

- **まぶたの中間** — 閉じた目の絵を途中の濃さで重ねると、細めた目・和らいだ目になる
- **頭の構え** — 傾き・上下・寄り。目の中点を軸に画像ごと動かすので、破綻しない
- **到着の動き** — 感情が変わった瞬間に減衰する揺れ。驚きは引き、喜びは弾む
- **頬の赤み** — 乗算で重ねる
- **呼吸の速さ** — 感情で変わる
- **話すときの頭の揺れ** — 口の開きに連動

傾けると枠の地色が出るので、タイルの背景に**その絵自身の背景色**を敷いている。

## 表情の絵の受け入れ判定

枠に絵を入れると、その絵が**その枠の役目を果たしているか**を自動で測る。

判定は「差の総量のうち帯の中の割合」ではだめだった。帯は画面の**約6%**しかないので、
面積が大きさに勝ってしまい、目だけを変えた本物の絵でも25%にしかならない。

正しいのは**密度の比**。

| | 帯の中の平均差 | 帯の外 | 集中度 |
|---|---|---|---|
| 本物の「閉じた目」 | 18.7 | 3.6 | **5.2** |
| 通常と同じ絵を入れた場合 | 3.2 | 2.2 | 1.4 |

### 大きさだけでは眉の絵を判定できない

眉を受け入れる段になって、この判定が**本物の眉の絵を落とす**ことが分かった。
内蔵の顔で5通り測った結果：

| 入れた絵 | 帯の中 | 帯の外 | 集中度 | 正しい判定 |
|---|---|---|---|---|
| 同じファイルを保存し直しただけ | 0.0 | 0.0 | 0.0 | 不合格 |
| 同じファイルを1px ずらしただけ | 2.9 | 2.9 | 1.0 | 不合格 |
| 眉を細い線で描き足した | **2.9** | 0.1 | **7.1** | **合格** |
| 眉を太い線で描き足した | 5.0 | 0.1 | 12.5 | 合格 |
| 顔全体を明るくした | 11.1 | 20.3 | 0.5 | 不合格 |

2行目と3行目は**帯の中の大きさが同じ 2.9 で、意味は正反対**。
眉は帯の中の細い線なので、動かす量がそもそも小さい。
区別できるのは**変化がどこに寄っているか**（集中度）だけで、2行目は1.0、3行目は7.1。

そこで「ほぼ同じ絵」と断じるのは、**変化が小さく、かつ帯の外にも散っている**ときだけにした。
小さくても帯の中に集中していれば、それは表情の弱い本物の絵なので、
落とさずに「変化は小さめ」と数値を添えて通す。作り直すかどうかは見た人が決める。

- 帯の中の変化が **4.5未満** かつ 集中度が **3.0未満** → 「ほぼ同じ絵」。作り直し
- 集中度が **1.8未満** → 「帯の外も変わっている」。重ねると顔がちらつく
- それ以外 → 合格。10未満なら「変化は小さめ」と添える

### 目の位置を平均で測ると、髪や服に引っ張られる

帯は目の位置から計算する。その目の位置は「通常」と「閉じた目」の差分から自動で求めていた。
やり方は、差が大きい点を左半分・右半分に分けて、それぞれの**重心**を取る、というもの。

これは「変わったのは目だけ」という前提に立っている。**その前提は成り立たない。**
同じキャラクターでも別々に生成した2枚は、髪の毛の流れも服のしわも違う。
右下に暗い差分のかたまりが1つあるだけで、右半分の重心はそこへ引きずられる。

実機からの報告と、それを再現した実験：

| | 左目 | 右目 | 傾き |
|---|---|---|---|
| 実機で起きたこと | 0.388, 0.301 | 0.713, **0.484** | **56%** |
| 差分のかたまりを1つ足して再現 | 0.389, 0.299 | 0.620, **0.420** | **55%** |

目の位置がこうなると、帯の計算（`eyeRegion` / `browRegion`）が総崩れになる。
実機の値では**目の帯が目より下にずれて鼻から口を覆い**、眉の帯は額から目まで広がった。
その結果、6枚中4枚が「◯以外も変化」で不合格になった。**絵は悪くない。物差しが狂っていた。**

直し方は、目について分かっていることを使う。**目は2つあり、水平に並び、左右に1つずつある。**

1. 差分を軽くぼかす（1点のノイズを消す）
2. 各行を「左半分の変化量と右半分の変化量の**小さいほう**」で採点する
   — 片側だけのかたまりでは点が上がらない。両目のある行だけが高得点になる
3. 最良の行の前後だけを見て、左右それぞれの**最大点**とその周りの小さな重心を取る

再現した壊れた例で 55% → **1%**。内蔵の絵での結果は 0.390,0.299 / 0.618,0.298 から
0.389,0.299 / 0.619,0.297 で、実質変わらない。

保険として、**傾きが間隔の25%を超えたら測定そのものを拒否**する。
拒否したときは黙って悪い値を使わず、「目の位置を合わせる」で手で指定するよう促す。

### 眉の帯が、額にあった

帯は目の間隔を基準に置いていた。`y: cy - sp*0.84` のように。
ところが `sp` は**画像の幅**に対する割合で、`y` は**高さ**に対する割合。
単位が違うものを引き算していた。3:2 の縦長画像では、意図した距離の**1.5倍**上に飛ぶ。

さらに定数そのものも実際の顔と合っていなかった。定規を当てて測った位置：

| | y | 目の線からの距離（目間隔） |
|---|---|---|
| 眉 | 0.252 – 0.272 | 上 0.17 – 0.29 |
| 目 | 0.283 – 0.315 | 上0.10 – 下0.11 |
| 目の線 | 0.298 | — |

旧設定の眉の帯は「目の線の上 0.24〜0.84 目間隔」。**眉は 0.17〜0.29 にあるので、帯の下端より下**、
つまり眉は**目の帯のほう**に入っていた。眉の絵の変化は「眉の帯の外で起きた」と採点され、
**まともな眉3枚が不合格になった**。

`bands_wrong_vs_right.png` が修正前後の帯（赤＝眉、青＝目）、
`brow_position_measured.png` が定規を当てて測ったもの。
数字ではなく顔に重ねて見たことで分かった。

修正後は眉 0.13〜0.42、目 −0.25〜0.13（目の線基準、目間隔単位）。
2つの帯は 0.13 のところで接し、重ならない。

### ずれただけの絵が、良い眉の絵に見える

帯を眉に合わせた副作用。眉は画像の中でも指折りの強いエッジなので、
**絵全体が1px ずれるだけで眉の帯が大きく光る**。実測（同じ絵を1pxずらしただけ）：
変化9.6、集中度3.4 で合格してしまう。

見分ける手がかりは2つある。ずれた絵は、
**変化の中心が帯の外**（フレーム端など最も強いエッジ）にあり、
**目の帯と眉の帯が同じくらい**変化する。

| | 変化の中心 | 眉帯内 | 目帯内 |
|---|---|---|---|
| 1px ずらしただけ | y0.992（帯は0.234–0.278） | 9.6 | 7.4 |
| 本物の眉の絵 | y0.250 – 0.273 | 13.0 – 19.6 | 7.5 – 8.2 |

両方に当てはまるときだけ「絵全体がずれている」として落とす。片方だけなら通す。

### 測っていない目の位置と、測った目の位置が見分けられなかった

目の位置の初期値は `{lx:0.40, ly:0.42, rx:0.60, ry:0.42}`、つまり画面の真ん中あたりの当て推量。
自分の絵を「通常」に入れると内蔵の顔は読み込まれず、「閉じた目」の枠が空になる。
すると自動測定が走らないので、**この当て推量のまま判定が行われる**。実測：

| 状態 | 帯の中 | 集中度 | 判定 |
|---|---|---|---|
| 自分の絵＋目の位置が初期値のまま | 0.0 | 0.0 | 6枚とも「ほぼ同じ絵」 |
| 同じ6枚＋目の位置を手で指定 | 1.5〜5.3 | **3.8〜13.2** | **6枚とも合格** |

**同じ絵が、全滅から全通過に変わる。**変わったのは目の位置だけ。
当て推量と実測が画面上で同じ顔をしていたのが原因なので、
`eyesSrc`（`default` / `auto` / `hand`）を持たせ、未測定なら判定そのものを無効と表示する。

### 帯が動いたら、判定はすべてやり直す

手で目の位置を指定しても、枠の下の判定は古いままだった。`reviewed[k]` が立ったきりで、
測り直しが走らない。**帯がずれていたせいで不合格になった絵が、直したあとも不合格のまま表示される。**
帯を動かす操作はすべて `rejudgeAll()` を通すようにした。

### 内蔵の絵が、自分で入れた絵を上書きしていた

「通常」を差し替えていない状態では `useBuiltIn()` が走るが、これが
**「閉じた目」も無条件で内蔵の絵に戻していた**。自分で「閉じた目」を入れても、
「通常」を差し替えるまでは、開くたびに消える。空のときだけ入れるようにした。

### 判定をまとめて持ち出す

判定は枠の下に一度出るだけで、次の絵を入れると消える。
画像そのものは端末から出ないので、こちらから絵は見られない。
そこで**「判定をまとめてコピー」**を置いた。8枠ぶんの状態
（読み込み済みか、保存されているか、変化・外・集中度・倍率・ずれ、目と口の位置）
を一つの文章にしてクリップボードへ入れる。これを貼れば、絵を見なくても診断できる。

コピー処理は `navigator.clipboard` だけを前提に書いてあり、
失敗したときに呼ぶ `fallback` が**定義されていなかった**。
非同期クリップボードを拒む環境では、ボタンが黙って例外を投げていたことになる。
`execCommand` による退避と、それも駄目なときに本文を画面に出す枠を足した。

### 読み込み順の不具合

端末に保存された表情の絵は、内蔵の「通常」より先に読み込みが終わることがある。
そのとき比較する相手が存在せず、判定も位置合わせも走らないまま素通りしていた。
「通常」が入った時点で、他の全部をもう一度見直すようにした。

## 絵を半透明で重ねると、弱い表情ではなく二重写しになる

表情の強さを**重ねる絵の不透明度**で表していた。強さ0.45なら上げ眉を45%で重ねる、という具合に。
瞬きも同じで、閉じた目の絵を0→1→0と重ねていた。

**これは間違いだった。**開いた目の絵50%と閉じた目の絵50%は、半分閉じた目にはならない。
**二重写し**になる。まぶたの線も眉の線も2本見える。

しかも常時見える。強さが途中で落ち着く表情（おだやか＝0.45）では、
**上げ眉が元の眉の上にずっと薄く重なったまま**になる。
瞬きは速いぶん一瞬だが、ramp が必ず中間を通るので毎回ちらつく。

手描きアニメーションはこれを溶明で解決したことがない。**カットする。**
1コマには1枚の絵しか出さない。

そこで、量は**どの絵を出すか**を決めるものに変えた（0.35以上なら出す、未満なら出さない）。
不透明度は常に1。強さは**溶明で表さず**、連続的に変えられるものだけで表す
——首の傾き、拡大、呼吸、頬の赤み、涙、到着時の動き。

`ghosting_dissolve_vs_cut.png` が修正前後。左の目が濁って二重になっているのが分かる。

同時に `squint`（目を細める＝閉じた目の絵を部分的に重ねる）を廃止した。
これが二重写しの中で最悪で、**表情が続くあいだずっとまぶたが2組**あった。
細めた目には細めた目の絵が要る。それが「笑う目」の役目。

### 帯のぼかしが、特徴の内側から始まっていた

重ねる絵は縁をぼかしてから貼っている。別々の生成なので、色が四角い境界で
急に変わると継ぎ目が見えるため。**そのぼかしの開始が外側68%の地点だった。**

眉は帯の半分の幅の**78%まで伸びている**。つまり**眉の先端がぼかしの中**にあり、
半透明で描かれ、その下から元の眉が透けていた。二重写しの第二の原因で、
実機の写真でも**先端だけ**が二重になっていた。

開始を86%に下げた。特徴を完全に覆い、最後の6分の1だけでなじませる。
そこは両方の絵とも同じ肌と髪なので、ぼかしても二重にならない。

## 保存が消える本当の理由

絵は選んだ瞬間に保存されている。それでも消える。**容量ではない。**

| | |
|---|---|
| 8枚の合計 | **0.83 MB** |
| ブラウザが報告する上限 | **967 MB** |

桁が3つ違う。原因は置き場所だった。このページは claude.ai の中の
**別オリジンの枠**で動いていて、**Safari はその位置から書かれた保存データを
「消していいもの」として扱う。**容量に関係なく、予告なく消える。
実機で6枚が「画面には出ているが保存されていない」状態になった。
IndexedDB も同じ規則の下なので、保存先を大きくしても解決しない。

そこで**控えをページ自身のデータベース（端末の外）に置いた。**
localStorage は速い経路として残す（顔はミリ秒で出さないといけない）。
控えは、ブラウザが捨てたものを開くたびに埋め戻す。
1文書は256KiB、1枚は約124KBなので入るが余裕は大きくないため、
超える絵は縮めて控える。**半分の幅で戻るほうが、空の枠より良い。**

呼び出しはすべて包んである。機能が無い環境でも、書き込みに失敗しても、
**以前とまったく同じ動作**になる。

## 画面が嘘をついていた3点

実機の写真から、いずれも報告されて分かった。

**① 例文のチップが白地に白文字。**あのボタンには CSS を1行も書いていなかった。
ブラウザ既定の明るいボタンのまま、`color:inherit` が文字にテーマの色
（ダークモードではほぼ白）を渡していた。

**② 「あなたの声がここに出ます」に何も出ない。**
その窓に書き込んでいたのは音声認識だけで、
**枠にマイクが渡らない端末では一度も動かない。**永久に placeholder のまま。
送った言葉は経路が違っても同じなので、そちらから書くようにした。

**③ 「ずっと聞いてもらう」を入れても何も変わらない。**
実際に何も起きていなかった。説明文の入れ替えと内部動作の変更だけで、
**目に見えることを何もしていない。**しかも肝心の
「端末側で音声コントロールをオンにする」はアプリの外にあり、
そこをやらなければ本当に何も起きない。

手順を並べ、**アプリにできない工程はそう明記**し、
アプリに分かる唯一のこと——**言葉が届いているかどうか**——を表示するようにした。
チェックボックスを、答えの出る検査に変えた。

## 顔を見ながら設定する

口の位置を合わせるには口が見えている必要があるが、動かす操作は画面のずっと下にあり、
そこまでスクロールすると顔が画面の外に出ていた。設定を開いているあいだだけ、
顔の列を上に固定する（`position:sticky`）。

**常時固定にしたら壊れた。**この列は残りの空間より背が高く、下の設定パネルに覆いかぶさる。
覆われるものの中に**「顔と声の設定」を開くボタンそのもの**が含まれていて、
助けるはずの操作がただ一つ届かない操作になった。開いているあいだだけ固定する。

拡大は、ピンチ／ホイール／ドラッグ／2回タップで戻す。
校正は「口の中心」「目の中心」を求めるが、等倍のスマートフォンでは数ピクセルしかない。
**拡大できるかどうかは、置けるか当てずっぽうかの差**になる。

### 座標の計算が4か所にあった

描画・帯の表示・目のタップ・口のタップが、それぞれ同じ計算を持っていた。
何も変わらないあいだは無害で、**変えた瞬間にバグになる**。
拡大を描画にだけ入れれば、指の位置と実際に置かれる位置がずれる。1か所にまとめ、
タップはその逆関数にした。

### 拡大の中心を保つ式を間違えた

「指の下にあるものが動かない」ようにする式として `view = m - (m - view)*k` を書いた。
**これは左上基準の式で、中央寄せには使えない。**中央寄せの項 `(W-iw)/2` は幅が変わると動く。
実測すると、2.5倍にしたあと**同じ画面位置のタップが 0.12 と 0.30 ずれた**。
「同じ割合の点が指の下に戻る」ように解き直した。ずれ 0.0000。

## 位置合わせをもう1段細かく

2段階の探索では、ずれの分解能が画面の 1/72 ——この絵では9ピクセル——しかなかった。
そのため小さなずれが測定に残り、すべての絵の下駄になっていた。
N=192 の3段目を足した。

効果は判定にも出た。**1ピクセルずらしただけの絵**が「合格」と出ていたのが、
位置合わせで補正されるようになり、残差がフレーム端に移って正しく落ちるようになった。

CPUを4倍遅くした状態で、7枚あわせて **886ms**。起動時に1回だけで、顔の表示は待たせない。

## 手を触れずに話す

音声入力には2種類あり、**ハンズフリーなのは片方だけ**。

| | 操作 | ハンズフリー |
|---|---|---|
| 音声入力キー（fn2回 / キーボードのマイク） | **発言ごとに押す** | ✗ |
| 音声コントロール（アクセシビリティ） | 一度オンにするだけ | **✓** |

後者に切り替えると、画面に触れずに会話が続く。ただし2つ実装が要った。

**① 自分の声を聞いてしまう。**音声コントロールは止まらないので、
澪の返事をスピーカー越しに拾って入力欄に打ち込み、それが自動送信され、
**彼女が自分自身と延々に会話する。**
そこで、澪が話している間（と、その後0.9秒）に入った文字は捨てる。
イヤホンを使えば根本的に起きないが、スピーカーでもループしないようにした。

**② 送信するとフォーカスが外れる。**音声入力はフォーカスのある欄に入る。
送信で欄を空にしたときにフォーカスも失っていたので、次の一言がどこにも入らず、
**結局画面を触ることになっていた。**送信後と、澪が話し終えた後にフォーカスを戻す。

## 眉をコードで作れないことの実測

`brow_warp_fails.png` が、彼女の絵から眉だけを取り出して動かそうとした結果。
上げる・困り・怒りの3通りとも、額と前髪が裂ける。

原因は単純で、**前髪が眉と同じ濃さ**だから。暗さで眉を選ぶと前髪も一緒に掴み、
動かすと髪が引きちぎられる。眉の下（まぶた）から肌を持ってきて塗り戻す方式でも同じ。

「絵でしか出せないもの」の境界はここにある。眉は Gemini に描いてもらうしかない。

## 画面の構成

会話中に見えるのは、顔・通話・入力・会話欄だけ。
枠の差し替え、口と目の位置合わせ、マイクの確認、記録は「顔と声の設定」に畳んである。

設定の案内（判定結果や測定値）は会話欄に混ぜない。設定の中に出す。
会話欄は澪との会話と、行動が必要なこと（マイクが使えない等）だけ。

## Gemini に渡す文面はアプリの中にある

6枚（上げ眉・困り眉・怒り眉・笑う目・見開く目・潤んだ目）の依頼文は、
「顔と声の設定」の中に、コピーボタン付きで入れてある。
別の画面から持ってくる必要はない。

どの文面も同じ形をしている。**変えない項目を先に全部並べ**、そのあとに変える1点、
最後に**目で確かめられる判定**を書く。これは、この絵を作り続けてきて分かったことで、
「真横にして」「無表情で」のような抽象的な言い方は効かず、
「見える手は1つだけ」「顔がまったく見えない」のように数えられる条件だけが通る。

「潤んだ目」だけ注意がある。**頬に涙の筋を描かせない。**
筋はアプリが動かして描くもので、絵に描いてあると二重になり、
しかも目の帯の外なので受け入れ判定にも落ちる。

## 結衣（Gemini Canvas 版）から取ったもの・取らなかったもの

同じ狙いの実装を別ルートで作ったものを読んだ。

**取ったもの**

- **仕草を返事ごとに選ばせる。** 感情とは別に `nod / tilt / shake` を返させる。
  悲しみながら頷く、明るいまま首をかしげる、はどちらも普通にある。
- **声に感情を乗せる。** 端末の読み上げは感情の指示を受け付けないので、
  速さと高さで出すしかない。喜び 1.07/1.13、悲しみ 0.92/0.98 など。
- **話題のきっかけ。** 何を話すか決まっていないときのための短い一言を並べる。

**取れなかったもの**

- **Gemini の音声合成**（`gemini-2.5-flash-preview-tts`、声 "Sulafat"）。
  端末の読み上げより明らかに良く、`Say cheerfully in Japanese:` のように
  感情を言葉で指示できる。ただし2つの理由で使えない。
  1. この画面のサンドボックスは `generativelanguage.googleapis.com` への通信を遮断する
  2. API キーと従量課金が要る（コストフリーという前提に反する）

**構造の違いとして記録しておくこと**

結衣は顔を**SVGのベクター**で持っている。だから眉が `d` 属性の差し替えだけで動く
（`eyebrowShapes` に default / empathy / smile / surprised が並んでいる）。
私が「ラスターの絵では眉を動かせない」と実測した問題を、
**絵をベクターにすることで回避している。**

代償は似顔絵としての一致で、実際に別人の顔になっている。
澪はGeminiが描いた絵そのものを使う方針なので、この交換はしない。
眉は絵で持つ、という結論は変わらない。

なお応答の遅さは構造から来ている。結衣は「対話API → 音声合成API」と
ネットワークを2回往復する。こちらは1回＋端末内の読み上げなので、その分だけ速い。
