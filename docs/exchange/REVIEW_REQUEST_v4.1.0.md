## 1. 何を実装したか(要約)

`docs/design/FEATURE_SPEC_v4.md` A章(ポイント)・B章(装備とショップ)の実装。
仕様書自体は変更していない。

| 機能 | 内容 |
|---|---|
| BP獲得 | 学習記録の保存時に「基本BP(1分=1BP)×倍率+行動ボーナス」を自動計算し`rec.bp`に確定。1日上限1,500BP、非受験科目は100BPまで |
| 受験科目チェック | 科目設定に「受験」トグルを追加(OFF=非受験科目) |
| 装備 | 衣装・スキル・ステージの3スロット(コーチ画面)。倍率は足し算で上限3.0倍 |
| ショップ | BPで衣装・スキル・ステージ・消費アイテムを購入。BP残高は「記録・ニュースの獲得BP合計 − 購入済みアイテムの価格合計」で毎回導出(別カウンタを持たない) |
| 消費アイテム | エナジードリンク(60分+1.0倍)・スポットライト(当日+0.5倍)・フィーバータイム(30分10倍・週1回)・リカバリー(連続記録の保険) |
| コンディション記録 | 生活習慣5項目(設定画面)。前日分が当日倍率+0.05〜+0.3に反映 |
| 今日画面 | 「学習を開始する」直下にブースト内訳カード(タップでモーダル) |

**今回のスコープ外**(意図的): 仲間コレクション・ワールドマップ・週末まとめ・ふるさとクエスト・金融ラボ・GT・PayPay。単元クリア(+200BP)・模試点数UP(+500BP)の自動判定も未実装(判定に必要な入力/比較ロジックがまだない)。

## 3. 自己レビューで見つけて直した問題(参考)

1. **`composeMultiplier`のフィーバー分岐で`breakdown.consumable`キーが欠落**しており、フィーバー発動中に「今日のブースト内訳」モーダルを開くと`undefined.toFixed`で例外→モーダルが開かない不具合があった。修正済み・回帰テスト追加済み。
2. **`defaultState()`が`DEFAULT_SUBJECTS`から`examSubject`フィールドをコピーし忘れていた**ため、新規ユーザーの「その他」科目が「非受験科目」として扱われず、100BP上限が効かないバグがあった。修正済み・回帰テスト追加済み。
3. **`streakDays()`の呼び出し箇所が8箇所あるうち4箇所で、リカバリー(連続記録の保険)の対象日リストを渡し忘れていた**(ポーズ解放判定・コーチの雑談・AIへの学習状況送信・別のコーチ台詞生成)。リカバリー使用時に画面ごとに連続日数の表示が食い違う不具合。修正済み。
4. **科目設定に追加した「受験」トグルが既存の`.toggle`(ノブ型スイッチ)を文字入り再利用**していたため、320px幅でラベル文字がノブに埋もれて判読不能、かつ科目名入力欄がほぼ0幅に潰れていた(実機ではなくPlaywrightスクリーンショットで実際に確認)。専用の`.mini-toggle-btn`(ラベル+ドット)に置き換え、行を2段組みに再構成して解決。
5. **新設の`.btn.small`CSSルールが、既存の記録画面ごみ箱「復元」ボタン(`class="btn small"`を以前から使用)を意図せず再スタイルしていた**。差分導入前は`.small`単体のfont-sizeユーティリティとしてしか効いていなかったが、`.btn.small`という複合セレクタを新設したことで既存ボタンのpadding・border-radiusまで変わってしまう不具合(見た目のみ・機能に影響なし)。ショップ用ボタンのクラス名を`.btn.compact`に改名して解決。

これら5件は、いずれも「自分自身によるコードレビュー」と「既存5画面への影響だけを見る、別プロセスでの独立した回帰レビュー」の2回に分けて実施した過程で発見した(4件目までは1回目、5件目は2回目の独立レビューで発見)。2回目のレビューでは上記5件目以外に新たな問題は見つからなかった(既存の8箇所の`streakDays`呼び出し・`celebrateAfterSave`のシグネチャ変更・`sanitizeState`の後方互換性・index.htmlのID重複なしなどを個別に確認済み)。

## 4. とくに見てほしい点(判断が割れそうな設計選択)

### 4-1. BP残高を「導出値」にした設計

BP残高用の独立したカウンタ(`state.bpBalance`のような数値)を持たず、
**毎回「記録・ニュースのbp合計 − 購入済みアイテムの価格合計」で計算し直す**設計にした。
理由: 別カウンタを持つと、記録削除・購入取り消しなどで実データとズレる不具合を作り込みやすいため。

**検証済み**: 記録5,000件(現実的な利用で到達しない規模)で`calcBpBalance`を100回連続実行しても23ms(1回0.23ms)。
配列を毎回舐めるだけの実装だが、体感できる遅さにはならないことを確認した。この点は確認不要。

### 4-2. 記録の編集ではBPを再計算しない

新規保存時に一度だけ`grantStudyBP()`を呼び、`rec.bp`を確定する。
**編集(時間の修正・振り返りの追記など)では再計算しない。**
理由: 編集のたびにBPが変わると、実績時間を何度も書き換えてボーナスを稼ぐ抜け道になるため。

**リスク**: 日付を間違えて保存し、あとで正しい日付に編集した場合、BPは「最初に保存した日の状況」のまま確定してしまう(たとえば装備を変える前に保存し、あとで日付だけ直しても倍率は変わらない)。仕様として妥当か、それとも「日付・科目の変更時だけは再計算する」べきか、判断を仰ぎたい。

### 4-3. 既存ユーザーの「受験科目」移行

新規ユーザーは「その他」科目がデフォルトで非受験科目になるが、**ver.4.0.0から引き継ぐ既存ユーザー(伊吹さん本人)は、全科目が「受験科目」扱いのまま**になる(`sanitizeState`は未設定フィールドを安全側=受験科目=true に倒すため)。
つまり伊吹さんの「その他」科目に100BP上限をかけたい場合は、設定→科目設定で手動でOFFにする必要がある。
**驚かせない設計を優先した意図的な選択だが、初回にトースト等で案内すべきか?**

### 4-4. リカバリー(連続記録の保険)の挙動

「使う」を押した**当日**を連続記録の対象日として保護する(`state.shop.streakGuardDates`に当日日付を追加)。
体調不良で休んだ**翌日以降**に「あの日を守っておけばよかった」と気づいて後から使うケースは想定していない
(過去の日付を選んで保護する導線がない)。仕様として十分か確認したい。
