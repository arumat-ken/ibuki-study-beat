## 2. 依頼内容の技術的な整理

**先に結論**: 依頼のうち **操作・音声・表情の設計は実現できる**。
**「1枚の写真から実写3Dモデル」の部分だけが、今日の道具では埋まらない。**
ここを飛ばして進むと、時間とお金を使ったあとで作り直しになる。

### 2.1 依頼を分解する

| 依頼 | 実現性 | 補足 |
|---|---|---|
| ChatGPT Live との音声会話 | ✅ できる | `AVATAR_TALK_DESIGN.md` で設計済み。Realtime API |
| 目と口の動き | ✅ できる | 3Dなら口の形6種+まばたきで足りる(4章) |
| 手足・体の動作との連動 | ✅ できる | ただし**動きは別に用意する必要がある**(2.4) |
| 指での拡大縮小・回転・上下移動 | ✅ **完成済み** | 8章。仕様確定・テスト14件合格 |
| 着せ替え | ⚠️ **今決める必要がある** | 「次のステップ」にはできない(3.4) |
| **1枚の画像から実写3Dモデル** | ❌ **今日は無理** | 2.2〜2.3 |

### 2.2 なぜ1枚の写真から3Dが作れないのか

写真は**見えている面だけ**を記録している。後頭部も、横顔の奥行きも、
腕の裏側も、写真には**存在しない**。3Dはそれらを全部必要とする。

「1枚から3D」を謳うツールはあるが、出てくるのは
**正面から見たときだけそれらしい、裏側が崩れた塊**で、
回して見る用途にも、関節を曲げる用途にも使えない。
**依頼には「指で回せる」と書いてある。**つまりこの方式は最初から選べない。

→ **だから Gemini の役割は「3Dを作ること」ではなく「3Dを作れる資料を揃えること」**。
8方向のターンアラウンド(全周を等間隔で撮った資料)を作る。これが5章。

### 2.3 grok のコンパニオンについて

比較対象として挙げられているが、あれは**画像から自動生成されたものではない**。
3Dの職人が、モデリング・骨入れ・表情作り・服の揺れの設定まで**手で作っている**。
絵柄も実写ではなくアニメ寄りで、これは技術的な逃げではなく**正しい判断**である。

実写の人間を3Dで動かすと、**不気味の谷**(よく出来ているほど、
わずかな不自然さが強い違和感になる現象)に落ちる。
静止画の実写は自然に見えるのに、**動いた瞬間に「死体が喋っている」ように見える**。
実写に寄せるほど、この谷は深くなる。

**ここは親の判断事項**(9章 未確定 #2)。実写を貫くか、
基準画像の面影を保ったまま少しだけ絵画寄りに倒すか。
後者のほうが、同じ予算で「良い」と感じられるものになる可能性が高い。

### 2.4 「手足・体の動作」について

3Dモデルは、置いただけでは棒立ちのまま**1ミリも動かない**。
動きは別に用意する必要があり、方法は3つ。

| 方法 | 内容 | 費用 | 質 |
|---|---|---|---|
| 既製のモーション | 配布・販売されている動きを買う(挨拶・うなずき・考える等) | 安い | 中。**体格に合わせる調整が要る** |
| 手付け | 3Dの職人が1つずつ作る | 高い | 高 |
| 計算で作る | 呼吸・重心の揺れ・うなずき。**2Dの設計で既に実装済み**(`core/motion.py`) | ゼロ | 「生きている感じ」限定 |

**現実的な組み合わせ**: 計算で作る動き(常時)+ 既製モーション8〜12種(場面ごと)。
2Dで作った `core/motion.py` の考え方はそのまま3Dでも使える。

## 3. 段階に分ける

一足飛びに Stage 3 へ行かない。**各段階で、動くものが手元に残る**ようにする。

| 段階 | 内容 | できること | 費用感 |
|---|---|---|---|
| **Stage 0** ✅ | 2Dの静止画 + 口パク + 表情 | 会話・口・表情・全身ポーズ切替 | 設計完了。画像26枚のみ |
| **Stage 1** | 2.5D(1枚の絵を部位ごとに分けて歪ませる) | 首が傾く・体が揺れる・目が動く。**回転はできない** | 小。Stage 0 の絵を使い回せる |
| **Stage 2** | 3D(骨入りモデル) | **指で回せる。**手足が動く | 大。3Dモデラーへの発注が現実的 |
| **Stage 3** | 着せ替え | 衣装の差し替え | Stage 2 の作り方次第で**ゼロにも作り直しにもなる** |

### 3.1 Stage 1 を飛ばさないほうがよい理由

依頼は Stage 2 を求めているが、Stage 1 は
**Stage 0 の絵をそのまま使え、費用がほぼかからず、見た目の改善が大きい**。
Stage 2 の準備(参照48枚の生成、モデラー探し、予算の判断)には時間がかかるので、
その間の手を止めないために挟む価値がある。

### 3.2 Stage 2 で「実写3D」を選ぶ前に

2.3 の不気味の谷は、**作ってから気づいても手遅れ**になる。
参照48枚が揃った時点で、**まず顔だけを試作して親が見る**こと。
全身と衣装3種を作りきってから判断すると、やり直しの損失が大きい。

### 3.3 iPhone で動かすということ

`AVATAR_TALK_DESIGN.md` の設計は **Python + パソコン**だった。
今回の依頼は iPhone なので、**土台が変わる**。

| | AVATAR TALK(既存設計) | AVATAR 3D(今回) |
|---|---|---|
| 動く場所 | Mac / Windows | **iPhone** |
| 言語 | Python | **Swift**(または Unity の C#) |
| 描画 | Qt で画像を重ねる | **RealityKit / SceneKit / Unity** |
| 音声 | `sounddevice` | **AVAudioEngine** |

**引き継げるのは「考え方」であって「コード」ではない。**
ただし次の3つは、そのまま移植できる形で確定済み。

1. **指の操作**(8章。テスト付きの参照実装)
2. **音量から口の開きを決める計算**(`core/lipsync.py`。dBFS化・追従・ヒステリシス)
3. **体の微妙な動き**(`core/motion.py`。呼吸・揺れ・うなずき)

### 3.4 ★着せ替えは「次のステップ」にできない

**依頼文で最も重要な誤解がここにある。**

> 次のステップでは着せ替えも自由に選択可能なモデルで準備してください

着せ替えは**あとから足せる機能ではない**。3Dモデルの**作り方そのもの**である。

| 作り方 | 着せ替え | あとから変更 |
|---|---|---|
| 服と体を1つの塊として作る(安い・速い) | **できない** | **不可能。作り直し** |
| 体を完成させ、服を別の層として重ねる | できる | — |

服を着た姿だけを作ると、**服の下の体は存在しない**。
服を脱がせると穴が開く。だから「あとで着せ替えを足す」は成立しない。

**したがって、Stage 2 の発注時点で「服を分ける」と決めておく必要がある。**
そのために、Gemini への指示(`avatar3d_multiview_prompts.json`)には
**`base_body`**(体のラインが分かるフィットしたスポーツウェア姿)を最初から入れてある。
これは表示には使わず、**体の形を決めるためだけ**の資料である。

**この一手だけで、Stage 3 が「作り直し」から「差分の追加」に変わる。**

## 5. Gemini への指示

正本: [`avatar3d_multiview_prompts.json`](avatar3d_multiview_prompts.json)

### 5.1 2Dのときと要求が正反対であること

| | 2Dの会話用(既存) | 3Dの参照用(今回) |
|---|---|---|
| 背景 | 街の遊歩道(演出) | **無地のグレーのみ** |
| 光 | 曇天の柔らかい光(演出) | **影が一切できない均一な光** |
| ポーズ | 自然な立ち姿 | **Aポーズ**(腕を斜め下45度) |
| 表情 | 感情をつける | **無表情** |
| 目的 | そのまま画面に出す絵 | **立体に起こすための設計図** |

**影は色として焼き付き、あとから取り除けない。**
雰囲気のある光は、3Dの資料としては汚れでしかない。
同じプロンプトを使い回してはいけない。

### 5.2 枚数(48枚)

| 種類 | 内訳 | 枚数 |
|---|---|---|
| ターンアラウンド | 8方向 × 4衣装(`base_body` / 基準の服 / カジュアル / フォーマル) | **32** |
| 顔のアップ | 正面・斜め45度・真横 | **3** |
| 表情 | 無表情・喜・怒・哀・楽・驚・閉眼 | **7** |
| 口の形 | ア・イ・ウ・エ・オ・閉じ | **6** |

8方向は `front` / `front_left_45` / `left` / `back_left_45` / `back` /
`back_right_45` / `right` / `front_right_45`。
**斜めが無いと、正面と横のあいだの形が推測になる。**

### 5.3 受け入れ条件(満たさない画像は3Dに使えない)

- [ ] 8方向を重ねたとき、身長と体の中心線が一致する
- [ ] **影が一切できていない**(顔の下・首・脇)
- [ ] 背景が無地のグレーで、切り抜きの境界がはっきりしている
- [ ] Aポーズが崩れていない。**指の本数を数える**
- [ ] **髪がなびいていない**(なびいた髪は立体に起こせない)
- [ ] 真横のカットで、鼻・唇・あごの出っ張りが読み取れる
- [ ] 真後ろのカットで、髪の量と流れが読み取れる
- [ ] 4衣装すべてで同じ体格・同じ身長に見える
- [ ] `base_body` で関節(肩・ひじ・手首・腰・ひざ・足首)の位置が分かる

## 8. Claude が完成させた部分 —— 指の操作

依頼のうち「指での拡大縮小、回転、上下移動」は、**仕様の確定まで完了**。
参照実装は `AVATAR_TALK_DESIGN.md` 付録 A-6(`core/camera.py`)。

### 8.1 操作の対応

| 指の動き | 動作 |
|---|---|
| 1本指ドラッグ | まわりを回る(左右は無制限、上下は±75度で止まる) |
| 2本指ピンチ | 寄る・引く(0.55〜4.50) |
| 2本指ドラッグ | 上下左右にずらす |
| 指を離す | 慣性で少し流れて止まる |
| ダブルタップ | 最初の位置へ戻す |

### 8.2 潰してある問題

素朴に作ると必ず踏む4つを、テストで固定してある。

| 問題 | 対処 |
|---|---|
| 真上を越えて像が反転し、操作の向きが逆になる | 上下を±75度で止める |
| ピンチが、寄っているときは大ざっぱ、引いているときは効かない | **引き算ではなく掛け算**で効かせる |
| 顔に寄っているとき、少し動かすと画面外へ飛ぶ | **ずらす量を距離に比例**させる |
| 端末のフレームレートで慣性の流れる量が変わる | 指数減衰を**積分した式**を使う |

### 8.3 フレームレート非依存の実測

指を離してから1秒後の回転角。**同じでなければならない。**

| 端末のフレームレート | この実装 | 素朴な実装(速度×dt を足すだけ) |
|---|---|---|
| 120Hz | 98.011° | 99.292° |
| 60Hz | 97.904° | 100.476° |
| 30Hz | 98.345° | 103.555° |
| 10Hz(処理が詰まったとき) | 97.901° | 113.993° |
| **ばらつき** | **0.44°** | **14.70°** |

素朴な実装だと、120Hz の iPhone と処理が詰まった瞬間とで
**流れる量が15%変わる**。「なんとなく滑りが悪い」の正体はこれ。

### 8.4 テスト

14件。`ruff` 指摘ゼロ、`pytest` 全56件合格(既存42件を含む)。
