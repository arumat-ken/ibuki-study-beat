## 1. 中核となる考え方 — 4つの時間を分離する

現在は「タイマーが表示した時間」がそのまま「実績」になり、そのまま「BPの対象」になっている。
ここを**3つに分ける**ことが、5経路のうち3つ(1・4・5)の根本対策になる。

| # | 名称 | 保存先 | 意味 | 使われる先 |
|---|---|---|---|---|
| A | **計画時間** | `rec.planMin` | 本人が事前に決めた時間 | グラフの計画棒、達成率 |
| B | **タイマー表示** | `activeSession` から都度計算(保存しない) | 開始からの時計上の経過。**参考値** | 画面表示のみ |
| C | **確認済み実績** | `rec.actualMin` | 本人が確認して保存した学習時間 | グラフの実績棒、累計時間、連続日数 |
| D | **BP対象時間** | `rec.bpMin`(新規) | Cのうち、BPを付けてよい時間 | BP計算のみ |

### 不変条件(実装で必ず守る)

```
D ≤ C                          BP対象は確認済み実績を超えない
D ≤ A + 明示的に延長した時間     計画を超えた分は、本人が延長を宣言しない限りBPにならない
B は D に自動で流れ込まない       タイマー表示は候補を出すだけ
```

**Bを直接Dにしない**、これが本設計の要点である。
Cは本人が「確かに勉強した」と言うなら尊重してよい(グラフには載せる)が、
Dは自動で膨らませない。

## 2. 経路1: 放置タイマー

### 現在の挙動

`openFinishModal` が `rec.actualMin + 経過分` を実績欄の初期値にする。
8時間放置して「保存」を押すと480分が実績になり、そのままBPになる(1日上限1,500BPまで)。

### 設計

**終了時の確認画面で、既定値を安全側に倒す。**

| 状況 | 判定 | 実績欄の既定値 | BP対象の既定値 |
|---|---|---|---|
| 経過 ≤ 計画 | 通常 | 経過時間 | 経過時間 |
| 計画 < 経過 ≤ 計画+15分 | 誤差の範囲 | 経過時間 | 経過時間 |
| 経過 > 計画+15分 | **超過** | **計画時間** | **計画時間** |
| 開始日 ≠ 保存日(日またぎ) | **放置の疑い** | **0分(未入力)** | **0分** |

超過・日またぎのときは、選択肢を明示する。

```
┌──────────────────────────────┐
│ 予定より 3時間20分 長く経っています      │
│                                        │
│ 計画 60分 / タイマー 240分              │
│                                        │
│  ● 計画どおり60分で終了      ← 既定    │
│  ○ 延長した  [ +30分 ][ +60分 ][ 分 ]  │
│  ○ 放置していた(記録しない)            │
│                                        │
│         [ この内容で保存する ]          │
└──────────────────────────────┘
```

- **既定は必ず「計画どおり」**。何も考えずに保存ボタンを押しても水増しにならない
- 「延長した」を選んだ分だけ、実績とBPに加わる
- 「放置していた」は実績0・BP0。連続記録も増えない
- 日またぎは既定を0分にし、**明示入力がなければ保存させない**

### 判断が必要な点(親・Codexへ)

- 誤差とみなす幅を **15分** としたが、これでよいか
- 延長の刻みを **+30分 / +60分 / 自由入力** としたが、自由入力を許すと水増しの余地が残る。
  上限を設けるべきか(例: 1回の延長は最大120分まで)

## 3. 経路2: 時間制アイテムの記録またぎ再利用

### 現在の挙動

フィーバー(30分)を発動 → 60分の記録を保存(30分が10倍) → **続けてもう1件保存すると、また30分が10倍**。
`activeBoosts` は期限が来るまで消えず、消費量を持たないため何度でも再利用できる。

### 設計

**発動中アイテムに「消費済み分数」を持たせ、実際に経過した時間を超えて使えないようにする。**

保存形式を次のように変える。

```js
// 現在
{ id, itemId, kind, expiresAt }

// 変更後
{ id, itemId, kind, startedAt, durationMin, consumedMin }
```

1件の記録が使える分数は次の**最小値**とする。

```
使える分数 = min(
    durationMin - consumedMin,              // アイテムの持ち時間の残り
    (現在時刻 - startedAt) の分数 - consumedMin  // 発動してから実際に経過した分の残り
)
```

BPを確定したら `consumedMin` に加算する。

### なぜ2つの上限が要るか

- **1つ目**がないと、持ち時間を超えて使える
- **2つ目**がないと、発動直後に長時間の記録を保存して持ち時間を先食いできる
  (10:00にフィーバー発動 → 10:01に「60分勉強した」と保存 → 30分ぶん10倍、実際は1分しか経っていない)

### 具体例

フィーバー(30分)を10:00に発動した場合:

| 操作 | 経過 | 使える分数 | 結果 |
|---|---|---|---|
| 10:05 に60分の記録を保存 | 5分 | min(30-0, 5-0)=**5分** | 5分が10倍。`consumedMin`=5 |
| 10:30 に60分の記録を保存 | 30分 | min(30-5, 30-5)=**25分** | 25分が10倍。`consumedMin`=30 |
| 10:45 にさらに保存 | 45分 | min(30-30, 45-30)=**0分** | 10倍は付かない |

合計30分ぶんだけが10倍になる。**アイテム名「30分間10倍」と一致する。**

エナジードリンク(60分)・スポットライト(その日1日)も同じ仕組みで扱う。
スポットライトは `durationMin` をその日の残り分数として扱う。

## 4. 経路3: ニュースの削除・復元による上限回避

### 現在の挙動

`todayCount` が `state.news` の現存件数のため、BP付きニュースを削除すると枠が空き、
4本目以降にもBPが付く。削除は「元に戻す」で復元できるため、BP付き4本以上を作れる。

### 設計

**「その日にBPを付与した回数」を、ニュースの現存件数とは別に記録する。**

```js
state.dailyNewsBp = {
  "2026-08-10": { count: 3, ids: ["n1", "n2", "n3"] }
}
```

- BPを付与するたびに `count` を増やし、`ids` に記録IDを追加する
- **削除しても `count` は減らない**(枠は戻らない)
- 同じIDが復元された場合、`ids` に含まれるので二重加算しない
- 上限判定は `state.news` ではなく `dailyNewsBp[date].count` を見る

あわせて、ニュースも学習記録と同じ**論理削除**(`deletedAt`)に変える。
現在は配列から物理的に削除しているため、削除・復元の履歴が追えない。

### トレードオフ(判断が必要)

入力ミスに気づいて削除し、正しく入れ直したい場合、**枠は戻らない**。
安全側に倒した設計だが、体験としては厳しい。代案として:

- **案A(採用推奨)**: 枠は戻さない。ただし「削除してもポイントの枠は戻りません」と画面に明記する
- **案B**: 保存から5分以内かつ未編集なら枠を戻す。悪用は理論上可能だが手間に見合わない
- **案C**: 1日あたりの「やり直し」を1回まで許す

Aを推奨する。理由は、ニュース記録は1〜2分の作業であり、
入れ直しのコスト(BP40〜60)より仕組みの単純さを優先したいため。

## 5. 経路4: 編集による日次上限・非受験科目上限の回避

### 現在の挙動

`grantStudyBP` は新規保存時のみ。編集で日付・科目・実績時間を変えても再評価されない。
このため:

- 別々の日に上限まで稼いだ記録を、あとから同じ日付へ移せる(合計は残る)
- 受験科目として保存した記録を、あとから非受験科目へ変えても100BP上限がかからない

### 設計

**BPを「保存時に確定した固定値」から「決定的に再計算できる値」に変える。**

記録に、BP計算に使った条件を保存する。

```js
rec.bpMin       // BP対象時間(§1のD)
rec.bpMultiplier // 保存時に適用した倍率(内訳ごと)
rec.bpActions   // 付与した行動ボーナスのキー
rec.bp          // 計算結果
```

編集で**日付・科目・実績時間**が変わったら、**その日(移動前・移動後の両方)のBPを再計算**する。
再計算は保存順に、日次上限・非受験科目上限を順に適用する。

### 編集でBPが増えないようにする

再計算を許すと、実績時間を増やしてBPを稼ぐ道ができる。これを塞ぐため:

```
rec.bpMin ≤ 初回保存時に確定した bpMin
```

つまり **編集でBPは減ることはあっても、増えることはない**。

- 実績を60分→30分に減らす → BPも減る(正しい)
- 実績を30分→60分に増やす → **グラフの実績は60分になるがBPは30分ぶんのまま**
- 日付を移動 → 移動先の日の上限が適用され、超過分は消える
- 科目を非受験科目に変更 → 100BP上限が適用される

「増やす方向の修正はBPに反映されない」ことは、編集画面に明記する
(Codexの以前の指摘「初回保存で確定することを編集画面にも短く表示」も、ここで満たす)。

## 6. 経路5: 小分け記録による行動ボーナスの水増し

### 現在の挙動

計画達成 +50 / 振り返り +10 / 模試 +300 が**記録1件ごと**に付く。
1分の記録を10件作れば +600BP。実際の学習は10分。

### 3つの案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A** | **1日1回まで**(連続日数ボーナスと同じ扱い) | 単純・確実・既存の`dailyBonuses`をそのまま使える | 予定を3件立てて全部達成しても+50のまま。頑張りが反映されない |
| **B** | **最低時間の条件**(実績15分以上の記録だけ対象) | 小分けのコストが上がる | 15分×10件=150分で+500BP。抑止はするが塞げない |
| **C** | **1日の行動ボーナス総額に上限**(例: 1日200BPまで) | 上限が明確。稼ぎ方の自由度は残る | 上限値の根拠が必要。模試+300が単独で超える |

### 推奨: A + B の組み合わせ

| ボーナス | 条件 |
|---|---|
| 計画達成 +50 | **1日1回**。かつ実績**15分以上**の記録が対象 |
| 振り返り +10 | **1日1回**。その日いずれかの記録に振り返りが書かれていれば付与 |
| 模試を受けた +300 | **1日1回**。かつ得点・満点が両方入力されている記録が対象 |
| 全受験科目 +80 | 現状どおり1日1回(PR #2で対応済み) |
| 連続日数 +30/+100/+500 | 現状どおり1日1回(PR #2で対応済み) |

**理由**: `FEATURE_SPEC_v4.md` A章の行動ボーナスは、文脈上いずれも「その日の達成」を表している。
「1日1回」が仕様の本来の意図に最も近く、実装も既存の `dailyBonuses` を流用できて単純である。
Bの最低時間を足すのは、1分の記録で日次ボーナスを取ってしまうのを避けるため。

**Aだけでは足りない点**: 予定を複数立てて全部こなした日が報われない。
これは行動ボーナスではなく、**学習時間そのもの(1分=1BP)で既に報われている**と考える。

### 判断が必要な点

- 最低時間を **15分** としたが妥当か
- 「予定を複数達成した日」を評価する別の仕組み(例: 予定3件達成で+30)を将来足すか
