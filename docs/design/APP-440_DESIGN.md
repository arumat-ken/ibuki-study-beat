## 1. 中核となる考え方 — 4つの時間を分離する

現在は「タイマーが表示した時間」がそのまま「実績」になり、そのまま「BPの対象」になっている。
ここを**3つに分ける**ことが、5経路のうち3つ(1・4・5)の根本対策になる。

| # | 名称 | 保存先 | 意味 | 使われる先 |
|---|---|---|---|---|
| A | **計画時間** | `rec.planMin` | 本人が事前に決めた時間 | グラフの計画棒、達成率 |
| E | **延長時間** | `rec.extendedMin`(新規) | 本人が完了画面で明示的に足した時間の合計 | A と合わせて上限になる |
| B | **タイマー表示** | `activeSession` から都度計算(保存しない) | 開始からの経過。**A+E で必ず頭打ちになる** | 画面表示のみ |
| C | **確認済み実績** | `rec.actualMin` | 本人が確認して保存した学習時間 | グラフの実績棒、累計時間、連続日数 |
| D | **BP対象時間** | `rec.bpMin`(新規) | Cのうち、BPを付けてよい時間 | BP計算のみ |

**宣言済み時間 = A + E** と呼ぶ。本人が「この時間は勉強する」と先に意思表示した時間である。

### 不変条件(実装で必ず守る)

```
タイマーは 宣言済み時間(A+E) で必ず停止する    宣言していない時間はカウントすらしない
C ≤ A + E                                    宣言していない時間は実績にも入らない
D ≤ C                                        BP対象は確認済み実績を超えない
B は D に自動で流れ込まない                    タイマー表示は候補を出すだけ
```

**設計の中核は「宣言していない時間は存在しないものとして扱う」ことである。**

初版では「超過してから確認画面で減らす」設計だったが、
**超過そのものを起こさせない**方式に改めた(親の確定方針 2026-08-10)。
勉強する意思が示されていない時間をタイマーがカウントし続けること自体をやめる。

これにより、初版で必要だった次の仕掛けが不要になった。

- 誤差の許容幅(15分の窓)
- 「超過したが記録だけ残す」選択肢 — 超過が発生しないため
- 超過時の実績とBPの食い違い — `C ≤ A+E` により C と D の乖離は「途中でやめた」場合だけになる

## 2. 経路1: 放置タイマー

### 現在の挙動

`openFinishModal` が `rec.actualMin + 経過分` を実績欄の初期値にする。
8時間放置して「保存」を押すと480分が実績になり、そのままBPになる(1日上限1,500BPまで)。

### 設計

**タイマーは宣言済み時間で自動的に停止する。超過を発生させない。**

親の確定方針(2026-08-10):

> 計画した時間で勉強でもテストでも完了してタイマーをストップして画面に完了の表示をする。
> 一方で、延長するのか休憩するのか、延長する場合は何分延長するのかを本人が意思を示すことで
> 加算するかしないかを決定する。本人の意思が明示されない場合はタイマーは完了しポイントも確定。
> **勉強する意思もないのにタイマーだけカウントする事はさせない。**

### 動作

| 時点 | 動作 |
|---|---|
| 開始 | 計画時間 A を宣言してタイマー開始。終了予定時刻 `endsAt = startedAt + A` が決まる |
| A 経過 | **タイマーが自動停止**。完了画面を出す。**この時点で C = D = A が確定** |
| 完了画面 | 「延長する」「休憩する」「今日はここまで」から選ぶ |
| 何も選ばない | **すでに確定済み。何も起きない。** カウントは進まない |

**BPは完了の時点で確定している。**完了画面のボタンは「今の記録が有効か」を問うものではなく、
「この先どうするか」を選ぶものである。放置しても損はせず、得もしない。

```
┌──────────────────────────────┐
│           完了！  60分                  │
│                                        │
│      60分ぶんのビートを獲得しました      │
│                                        │
│  ┌────────────────────────┐  │
│  │ 延長する                          │  │
│  │  [+5][+10][+15][+30]  [ ‑ 5分 ＋ ] │  │
│  │            最長60分                │  │
│  └────────────────────────┘  │
│                                        │
│  [ 休憩する ]      [ 今日はここまで ]   │
└──────────────────────────────┘
```

### 延長

- **5分刻み、1回あたり最長60分**(親の確定 2026-08-10)
- 延長を選ぶと `E` に加算され、`endsAt` が後ろへ伸びる
- 延長した時間が経過すると、**同じ完了画面がもう一度出る**。さらに延長したければ再度宣言する
- 延長は何度でもできる。**毎回が明示的な意思表示**になる
- 日次上限(1,500BP)と非受験科目上限(100BP)は従来どおり効く

### 記録の種類による違い

親の確定方針(2026-08-10):

> テストなんかは超過はありえないので、決められた時間の記録だけになる。
> 一方で、勉強時間は消化しても記録するようにする。

| 種類 | 延長 | 完了画面のボタン | 理由 |
|---|---|---|---|
| 学習 | **できる** | 延長する / 休憩する / 今日はここまで | 予定より長く勉強することは実際に起きる |
| テスト・模試 | **できない** | 完了 / 今日はここまで | 試験時間は決まっており、超過はありえない |

テスト記録では完了画面に延長のボタンを出さない。
決められた時間ちょうどで完了し、その時間だけが記録される。

### 延長は記録に残す

親の確定方針(2026-08-10):

> 基本は決めた時間でやり切るという形を身につけさせたいので、
> 一旦予定時間になったら明示的に延長するかどうかを本人の意思によって決めさせ、記録に残す対象とする。

延長を実績時間へ黙って溶かし込まない。**「予定どおりに終わらなかった」事実として別に残す。**

```js
rec.planMin     = 60    // 最初に宣言した計画
rec.extendedMin = 30    // 完了画面で明示的に足した合計
rec.actualMin   = 90    // C(確認済み実績)
rec.bpMin       = 90    // D(BP対象)
```

記録詳細と記録一覧では **「計画60分 ＋ 延長30分 = 実績90分」** と分けて表示する。

**グラフの仕様は変更しない。**計画棒・実績棒・累積線の描画は従来どおりで、実績棒は90分のまま。
(グラフ中核仕様の変更禁止という制約に従う。延長の内訳は記録側で見せる)

**狙い**: 延長すること自体は悪くない。ただし「決めた時間でやり切る」を基本形として身につけるため、
延長したなら**意思をもって延長したと本人にも見えるようにする**。
これは「最初の予定より長く勉強した」場合の扱いと同じ考え方で揃えてある。

### 休憩する

- タイマーを止め、その時点までのBPを確定する(すでに確定済みなので追加確定はない)
- 休憩中は**一切カウントしない**
- 「再開」を押すと、新しい計画時間を宣言して次のセッションを始める
- 休憩と「今日はここまで」の違いは、再開の導線を画面に残すかどうかだけ。BPの扱いは同じ

### 途中でやめた場合(計画未満)

「今日はここまで」を計画時間より前に押した場合は、**その時点までの経過**が C = D になる。
減る方向なので水増しにはならない。

### アプリを閉じていた場合(重要)

**停止はイベントではなく計算で決める。**通知や `setTimeout` に依存してはならない。
iPhoneは画面を消すとタイマーが動かないことがあり、アプリが終了させられることもある。

次にアプリを開いたとき、次の式で終了時刻を確定する。

```js
var endsAt = session.startedAt + (session.planMin + session.extendedMin) * 60000;
var endedAt = Math.min(now, endsAt);      // 宣言済み時間を超えない
var elapsedMin = Math.floor((endedAt - session.startedAt) / 60000);
```

- `now > endsAt` なら、**セッションは `endsAt` に完了していた**ものとして扱う
- 完了画面を出し、「◯時◯分に完了していました」と伝える。**見逃さない**
- `endsAt` を超えた分は C にも D にも入らない。**捨てる**
- 日をまたいでいても同じ。宣言済み時間しか入らないので、放置による水増しは起こらない

この「計算で決める」方式により、日またぎの特別扱いが不要になった。
初版の「日またぎは既定0分・未入力では保存させない」という規則は、
そもそも日をまたぐほど長い宣言をしていない限り発生しないため削除する。

### 手入力の記録との関係

タイマーを使わず実績時間を直接入力する経路は従来どおり残す。

親の確定方針は「**勉強する意思もないのにタイマーだけカウントする事はさせない**」である。
手入力は本人が数字を打つ行為そのものが意思表示であり、
「意思のないカウント」には当たらない。したがって宣言済み時間の上限はかけない。

| 経路 | 実績の上限 | 時間制アイテム | 装備・コンディション | 日次上限 |
|---|---|---|---|---|
| タイマー | 宣言済み時間(A+E)で頭打ち | 実学習区間の重なりぶん | 適用 | 適用 |
| 手入力 | 入力値をそのまま採用 | **適用しない**(§3) | 適用 | 適用 |

**手入力に時間制アイテムを適用しない**ことが、この方針を成り立たせる条件である。
適用してしまうと、アイテムを発動して手入力で長時間を打ち込むだけで
タイマー側で塞いだ経路が復活する(§3「手入力の記録とアイテム」)。

残るのは「実際には勉強していない時間を手で打ち込む」という**能動的な虚偽入力**だけで、
これは**日次上限1,500BP**で頭打ちになる。

なお「1,500BP = 1日◯時間ぶん」という時間換算はしない。倍率と行動ボーナスがあるため、
同じ1,500BPに対応する学習時間は状況によって変わる。上限の根拠を時間換算に求めない。

受動的・偶発的な水増し(放置)とは性質が異なるため、仕組みでは塞がない。

### この方式が塞ぐもの

| 初版で必要だった仕掛け | 新方式 |
|---|---|
| 誤差の許容幅(15分) | **不要**。超過が起きない |
| 超過時の確認画面と既定値 | **不要**。超過が起きない |
| 「記録だけ残す」選択肢 | **不要**。宣言外の時間は実績にも入らない |
| 日またぎの特別扱い | **不要**。宣言済み時間しか入らない |
| 8時間放置 → 480分 | **発生しない**。60分で停止している |

## 3. 経路2: 時間制アイテムの記録またぎ再利用

### 現在の挙動

フィーバー(30分)を発動 → 60分の記録を保存(30分が10倍) → **続けてもう1件保存すると、また30分が10倍**。
`activeBoosts` は期限が来るまで消えず、消費量を持たないため何度でも再利用できる。

### 設計

**アイテムは「実際に勉強していた時間」にだけ使われる。**

§2でタイマーが宣言済み時間で自動停止するようになったため、
「壁時計の経過」ではなく**実際の学習区間**を基準にできる。両者は一致しない。

```
10:00 学習開始・フィーバー発動
10:10 一時停止
10:40 再開
10:50 終了

壁時計の経過 = 50分   ← 一時停止の30分を含んでしまう
実際の学習   = 20分   ← 10:00〜10:10 と 10:40〜10:50
```

初版は壁時計を使っていた。**一時停止して放置するだけでアイテムを消費でき、
勉強していない時間に倍率がかかる**ため、実学習区間を基準に改める。

### 学習区間を記録する

セッションに**実際に勉強していた区間**を持たせる。

```js
state.activeSession = {
  recordId, startTs, pausedAccum, pausedAt,
  segments: [ { from: 1786400000000, to: 1786400600000 }, ... ]   // 新規
}
```

| 操作 | segments の扱い |
|---|---|
| 開始 | `[{ from: startTs, to: null }]` |
| 一時停止 | 最後の区間の `to` に現在時刻を入れる |
| 再開 | 新しい区間 `{ from: 現在時刻, to: null }` を足す |
| 終了・自動停止 | 最後の区間の `to` に終了時刻を入れる |

`to` が `null` の区間は「いま進行中」を表す。表示時は `min(now, endsAt)` で閉じる。

**確認済み実績 C は segments の合計**になる。

新形式では **`segments` を時間制アイテム判定の唯一の根拠**とする。
`pausedAccum` はCの計算には使わない(新規セッションでは常に `segments` がある)。

#### `segments` の**有無**が新旧の判別そのものである

```js
var isNewFormat = Array.isArray(session.segments);   // フィールドの有無で判別する
C = isNewFormat
  ? segments の合計
  : now - session.startTs - (session.pausedAccum || 0);   // 従来式
```

したがって **空配列 `segments: []` を書き込んではならない。**
書き込むと新形式と判定され、合計0分がCになり、**移行前の実績を失わせる。**

| 状態 | 意味 | Cの求め方 |
|---|---|---|
| `segments` が**未定義** | 旧セッション(移行中) | **従来式**で保つ |
| `segments` が `[]`(空配列) | **作ってはならない状態** | — |
| `segments` に1件以上 | 新形式 | 区間の合計 |

区間を追加する処理は、**本人が「再開」を押した時に初めてフィールドごと新設する**。
それ以外の経路で `session.segments` へ代入しない。

### アイテムが使える分数

**時間はすべてミリ秒で保存・比較し、丸めるのはBPを確定する最後の一度だけ**とする。
分単位で途中計算すると、切り上げ・切り捨てのたびに誤差が積み上がる。

```
アイテムの有効区間 = [ startedAt, startedAt + durationMs ]
overlapMs = Σ ( segments の各区間 ∩ アイテムの有効区間 の長さ )
```

```js
availableMs = Math.max(0, Math.min(
  durationMs - consumedMs,   // 持ち時間の残り
  overlapMs  - consumedMs    // 実際に勉強していた時間のうち、まだ使っていない分
));
appliedMs   = availableMs - (availableMs % 60000);   // 分未満は切り捨てる
boostMinutes = appliedMs / 60000;
consumedMs  += appliedMs;                            // 丸めた後の分だけを消費する
```

**`consumedMs` に足すのは `appliedMs`(丸めた後)であって `availableMs` ではない。**
これが端数の扱いを一意に決める。

| 書き方 | 59秒のとき | 問題 |
|---|---|---|
| `consumedMs += availableMs` | 59秒を消費 | 次の1秒と合算できず、**端数を失う** |
| 消費しないが式で保証しない | — | 次回に同じ59秒を**重ねて使える** |
| **`consumedMs += appliedMs`** | **消費しない** | 次回へ持ち越せて、二重にもならない |

`Math.max(0, …)` は必須である。期限切れや既消費の状態で負の値になるのを防ぐ。

### 端数の動き(検算済み)

| 状況 | `availableMs` | `appliedMs` | 倍率がかかる分数 | `consumedMs` |
|---|---|---|---|---|
| 59秒学習して保存 | 59,000 | 0 | **0分** | 0(据え置き) |
| さらに1秒学習して保存 | 60,000 | 60,000 | **1分** | 60,000 |
| 有効期限まで59秒の状態で保存 | 59,000 | 0 | **0分** | 据え置き |
| その後、期限を過ぎて保存 | 0 | 0 | **0分** | 据え置き。**持ち越さない** |
| 期限切れかつ消費済み | 0(負にならない) | 0 | **0分** | 据え置き |

`consumedMs` の意味は「**BP確定で実際に消費した学習時間**」であり、
壁時計の経過や有効期限までの残り時間とは別物である。混同しない。

### なぜ2つの上限が要るか

- **1つ目**がないと、持ち時間を超えて使える
- **2つ目**がないと、発動直後に長時間の記録を保存して持ち時間を先食いできる
  (10:00にフィーバー発動 → 10:01に「60分勉強した」と保存 → 30分ぶん10倍、実際は1分しか経っていない)

### 具体例

フィーバー(30分)を10:00に発動した場合:

| 操作 | 実学習の重なり | 使える分数 | 結果 |
|---|---|---|---|
| 10:05 に記録を保存 | 5分 | min(30-0, 5-0)=**5分** | 5分が10倍。`consumedMs`=5分ぶん |
| 10:05〜10:20 一時停止 | 増えない | — | 停止中は消費しない |
| 10:30 に記録を保存 | 15分(10:20〜10:30を追加) | min(30-5, 15-5)=**10分** | 10分が10倍。`consumedMs`=15分ぶん |
| 10:45 にさらに保存 | 30分 | min(30-15, 30-15)=**15分** | 15分が10倍。`consumedMs`=30分ぶん |
| その後 | — | min(30-30, …)=**0分** | 10倍は付かない |

合計30分ぶんだけが10倍になる。**アイテム名「30分間10倍」と一致する。**

一時停止した15分はどの段階でも消費されない。**勉強していない時間に倍率はかからない。**

エナジードリンク(60分)も同じ仕組みで扱う。
スポットライトは有効区間をその日の残り全体とする。

### 手入力の記録とアイテム

タイマーを使わない手入力の記録には**学習区間が存在しない**。
このため**時間制アイテムの倍率は適用しない**。

適用してしまうと、アイテムを発動してから手入力で長時間を打ち込むだけで
持ち時間を丸ごと使えてしまい、§2で塞いだ経路が手入力側から復活する。

| 経路 | 時間制アイテム | 装備・コンディション |
|---|---|---|
| タイマー | 実学習区間の重なりぶんだけ適用 | 適用する |
| 手入力 | **適用しない** | 適用する |

装備とコンディションは時間に紐づかない常時効果のため、手入力にも適用する。
この違いは、手入力の画面と記録詳細に明記する。

### 消費は取り消せない(編集・削除・復元後の扱い)

**一度BPに使った `consumedMs` は、記録を編集・削除・復元しても解放しない。**

```
consumedMs は単調増加する。いかなる操作でも減らさない。
```

解放すると、次の抜け道が生まれる。

```
10:30 フィーバー発動中に60分の記録を保存  → consumedMs = 30分ぶん(使い切り)
10:31 その記録を削除                      → もし解放すると consumedMs = 0
10:32 別の記録を保存                      → また30分が10倍
```

削除・復元を繰り返すだけで、同じ発動時間を何度でも別の記録へ配り直せてしまう。
したがって**消費は発動側(`activeBoosts`)に記録し、記録側の生死とは切り離す**。

| 操作 | `rec.bp` | `consumedMs` |
|---|---|---|
| 記録を削除 | 集計から外れる(論理削除) | **変わらない** |
| 削除した記録を復元 | 集計に戻る。再計算はしない | **変わらない** |
| 記録の実績を減らす編集 | 減る | **変わらない** |
| 記録の実績を増やす編集 | 増えない(§5の規則) | **変わらない** |

削除した記録のBPが戻らないことは、体験としては厳しい方向である。
ただし「使ったアイテムの効果時間は戻らない」ことはアイテムの意味として自然であり、
削除・復元による再配分を許すほうが害が大きいと判断した。
この扱いは購入前の説明文とショップ画面に明記する。

## 4. 経路3: ニュースの削除・復元による上限回避

### 現在の挙動

`deleteNews` は `state.news` から要素を取り除き、トーストの「元に戻す」で
**`bp` を保持したまま同じ位置へ戻す**(`js/app.js:1668-1678`)。
上限判定 `todayCount` は `state.news` の現存件数を見ている。

```
1. ニュースを3本記録        → 3本ともBPあり(1日3本が上限)
2. 3本目を削除             → 残り2本。BPも消える。枠が空く
3. 4本目を記録             → 空きがあるのでBPが付く
4. 「元に戻す」を押す        → 3本目がBPを持ったまま復活
                          → BP付きが4本になる
```

**問題は「削除で枠が戻ること」ではなく、「元に戻すが枠の状況を見ずにBPごと復活させること」である。**

### 設計

親の確定方針(2026-08-10):

> 予定していたニュースを自分で入れたことによってボーナスが発生したけども、
> 取りやめたときには**なかったことになる**。

**削除は「なかったこと」にする。BPも消え、枠も戻る。**これは現在の挙動と同じで、正しい。
直すのは「元に戻す」だけである。

| 操作 | ニュース | BP | 枠 |
|---|---|---|---|
| 記録する | 追加 | 枠が空いていれば付与 | 1つ消費 |
| 削除する | 取り除く | **消える** | **戻る** |
| 元に戻す(枠が空いている) | 戻る | **復活する** | 1つ消費 |
| 元に戻す(**枠が埋まっている**) | 戻る | **付かない(bp=0)** | 消費しない |

復元時に枠が埋まっていた場合は、ニュース自体は戻すが `bp = 0` にし、
**「1日3本の上限に達しているため、ポイントは戻りませんでした」**と画面に表示する。

### 実装

上限判定は「その日のBP付きニュースの現存件数」を**その都度数える**。

```js
function newsBpCountOn(state, date) {
  return (state.news || []).filter(function (n) {
    return n.date === date && (n.bp | 0) > 0;
  }).length;
}

function canGrantNewsBp(state, date) {
  return newsBpCountOn(state, date) < NEWS_BP_DAILY_LIMIT;   // 3
}
```

追加時も復元時も、同じ `canGrantNewsBp` を通す。これだけで不変条件が成り立つ。

```
どの時点でも、同じ日のBP付きニュースは最大3本
```

### 台帳(`dailyNewsBp`)は作らない

初版では「その日にBPを付与した**回数**」を別台帳に記録し、削除しても減らさない設計だった。
これは撤回する。理由は3点。

1. **親の意図と違う。** 削除は「なかったこと」であり、枠が戻らないのは直感に反する
2. **移行が必要になる。** 旧データに台帳が無いため復元処理が要り、判別不能な場合の安全側の扱いも要る
   (Codexの差し戻し2はこの移行についての指摘だった)
3. **不要である。** 削除時にBPも消えるため、現存件数を数えるだけで上限を守れる

台帳をやめることで、**移行処理そのものが不要**になる。新しい保存フィールドも増えない。

### 削除で BP残高 が減ることについて

BP残高は `state.news[].bp` の合計から計算しているため、削除すると残高が減る。
既にショップで使っていた場合、残高は `Math.max(0, 稼いだ - 使った)` により0で止まり、
購入済みのアイテムは失われない。

**これは現在も同じ挙動であり、本設計による変更ではない。**
「削除するとポイントも取り消されます」と削除確認に明記する。

### 論理削除は導入しない

初版ではニュースにも学習記録と同じ論理削除(`deletedAt`)を入れる案だったが、
上限を現存件数で数える方式では不要なため見送る。
現在の「物理削除＋トーストによる取り消し」を維持し、復元時の判定だけを直す。

## 5. 経路4: 編集による日次上限・非受験科目上限の回避

### 現在の挙動

`grantStudyBP` は新規保存時のみ。編集で日付・科目・実績時間を変えても再評価されない。
このため:

- 別々の日に上限まで稼いだ記録を、あとから同じ日付へ移せる(合計は残る)
- 受験科目として保存した記録を、あとから非受験科目へ変えても100BP上限がかからない

### 設計

**BPを「保存時に確定した固定値」から「決定的に再計算できる値」に変える。**

記録に、BP計算に使った条件を保存する。

```js
rec.bpMin       // BP対象時間(§1のD)
rec.bpMultiplier // 保存時に適用した倍率(内訳ごと)
rec.bpActions   // 付与した行動ボーナスのキー
rec.bp          // 計算結果
```

編集で**日付・科目・実績時間**が変わったら、**その日(移動前・移動後の両方)のBPを再計算**する。

### 再計算の順序を固定する

上限は「先に来た記録から順に配る」ため、**順序が変わると同じデータでもBPが変わる**。
画面の操作順や配列の並びに依存させてはならない。次の順序で決定的に並べ替える。

```js
function bpOrder(a, b) {
  if (a.createdAt !== b.createdAt) return a.createdAt < b.createdAt ? -1 : 1;  // 1) 作成日時の昇順
  return a.id < b.id ? -1 : (a.id > b.id ? 1 : 0);                            // 2) 同時刻なら記録IDの昇順
}
```

| 規則 | 内容 |
|---|---|
| 第1キー | `rec.createdAt`(作成日時)の昇順。**編集しても変わらない値**を使う |
| 第2キー | `rec.id` の昇順。`createdAt` が同一でも一意に定まる |
| 使わない値 | `state.records` の配列順、`updatedAt`、画面の表示順 |

`createdAt` を持たない旧データは、`sanitizeState` で `rec.id` から復元するか、
復元できなければ**その日の最古**として扱う(既に上限内で確定済みのため、順序が変わっても総額は動かない)。

この順序で、日次上限 → 非受験科目上限 → 行動ボーナスの順に適用する。
**同じ記録集合からは、何度再計算しても同じBPが出る**ことを不変条件とする。

### 編集でBPが増えないようにする

再計算を許すと、実績時間を増やしてBPを稼ぐ道ができる。これを塞ぐため:

```
rec.bpMin ≤ 初回保存時に確定した bpMin
```

つまり **編集でBPは減ることはあっても、増えることはない**。

- 実績を60分→30分に減らす → BPも減る(正しい)
- 実績を30分→60分に増やす → **グラフの実績は60分になるがBPは30分ぶんのまま**
- 日付を移動 → 移動先の日の上限が適用され、超過分は消える
- 科目を非受験科目に変更 → 100BP上限が適用される

「増やす方向の修正はBPに反映されない」ことは、編集画面に明記する
(Codexの以前の指摘「初回保存で確定することを編集画面にも短く表示」も、ここで満たす)。

## 6. 経路5: 小分け記録による行動ボーナスの水増し

### 現在の挙動

計画達成 +50 / 振り返り +10 / 模試 +300 が**記録1件ごと**に付く。
1分の記録を10件作れば +600BP。実際の学習は10分。

### 3つの案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A** | **1日1回まで**(連続日数ボーナスと同じ扱い) | 単純・確実・既存の`dailyBonuses`をそのまま使える | 予定を3件立てて全部達成しても+50のまま。頑張りが反映されない |
| **B** | **最低時間の条件**(実績15分以上の記録だけ対象) | 小分けのコストが上がる | 15分×10件=150分で+500BP。抑止はするが塞げない |
| **C** | **1日の行動ボーナス総額に上限**(例: 1日200BPまで) | 上限が明確。稼ぎ方の自由度は残る | 上限値の根拠が必要。模試+300が単独で超える |

### 推奨: A + B の組み合わせ

| ボーナス | 条件 |
|---|---|
| 計画達成 +50 | **1日1回**。かつ実績**15分以上**の記録が対象 |
| 振り返り +10 | **1日1回**。その日いずれかの記録に振り返りが書かれていれば付与 |
| 模試を受けた +300 | **1日1回**。かつ得点・満点が両方入力されている記録が対象 |
| 全受験科目 +80 | 現状どおり1日1回(PR #2で対応済み) |
| 連続日数 +30/+100/+500 | 現状どおり1日1回(PR #2で対応済み) |

**理由**: `FEATURE_SPEC_v4.md` A章の行動ボーナスは、文脈上いずれも「その日の達成」を表している。
「1日1回」が仕様の本来の意図に最も近く、実装も既存の `dailyBonuses` を流用できて単純である。
Bの最低時間を足すのは、1分の記録で日次ボーナスを取ってしまうのを避けるため。

**Aだけでは足りない点**: 予定を複数立てて全部こなした日が報われない。
これは行動ボーナスではなく、**学習時間そのもの(1分=1BP)で既に報われている**と考える。

### 最低時間 15分 について(親の確定 2026-08-10)

> 計画達成の最低時間15分というのは内容によりますが、一旦それで進めます。
> 例えば単語10個覚える、漢字を20個書く、歴史・地理・世界史・日本史などの用語を記憶するなど、
> ミニテストなんかも含め15分で完了させる勉強もあると思います。

**15分を採用する。条件は「実績15分以上」で、15分ちょうども対象に含める。**

単語10個・漢字20個・用語の暗記・ミニテストのように、
**短時間で完結する正当な勉強を弾かないこと**が判断の根拠である。
「15分を超える」ではなく「15分以上」とする点を実装で必ず守る(境界値試験 T-5-6)。

### 判断が必要な点(将来の検討)

- 「予定を複数達成した日」を評価する別の仕組み(例: 予定3件達成で+30)を将来足すか

### 発動中アイテムの移行(Q7・Q12の決着)

初版は `consumedMin = durationMin - 残り時間` としていたが、**2つの誤りがあった。**

1. `Math.ceil((expiresAt - now) / 60000)` は残り1秒を1分として扱う。
   「得も損もしない」という説明と一致しない
2. `consumedMin` は「**BP確定で消費した実学習時間**」であり、
   「有効期限までの残り時間」とは意味が違う。差し引く対象として不適切

**採用する方式: 消費量には触れず、有効区間だけを逆算する。**

```js
var durationMs = ITEM_DURATION_MS[old.itemId];        // 30分 / 60分 などの定義値
{
  startedAt:  old.expiresAt - durationMs,             // 有効区間の開始を逆算
  durationMs: durationMs,
  consumedMs: 0                                       // 過去の消費は仮定しない
}
```

`consumedMs = 0` でも**得にはならない**。使えるのは
「**移行後に作られた `segments` と、アイテムの有効区間の重なり**」だけであり、
有効区間は `expiresAt` で終わるためである。

| 状況 | 移行後に使える上限 |
|---|---|
| フィーバー(30分)を発動して10分経過 | **残り20分の壁時計の間に勉強した分**だけ |
| 発動して30分経過(期限切れ) | **0分**。有効区間が既に終わっている |
| 発動直後 | 残り30分の間に勉強した分だけ |

移行前の未保存時間には `segments` が無いため、**さかのぼって使われることもない**(§8「旧セッションの移行」)。

**過去の消費量を仮定しないため、Q11の移行方式と矛盾しない。**

### 旧セッションの移行(Q11の訂正)

初版は「`startTs` と `pausedAccum` から1区間 `{ from: startTs, to: null }` を作れば
合計時間は一致する」と書いていたが、**これは誤りである。**

```
10:00開始 / 10:10〜10:20一時停止 / 10:30時点

現行式の実績        = 10:30 - 10:00 - 10分 = 20分
1区間で復元した値   = 10:30 - 10:00        = 30分   ← 一致しない
```

さらに、**過去の一時停止がどこにあったかは旧データから復元できない。**
区間を推測して作ると、アイテムBPを過大にも過小にもしうる。

**採用する方式: 実績は従来式で保ち、分からない区間には倍率を付けない。**

| 対象 | 扱い |
|---|---|
| 確認済み実績 C | **従来式で保つ**(`now - startTs - pausedAccum`)。**時間を失わせない** |
| 時間制アイテム | 移行前の未保存時間には**適用しない**。`segments` が無い区間は根拠が無いため |
| 移行後 | 本人が明示して再開した時点から、新しい区間 `{ from: 再開時刻, to: null }` を作る |
| 一時停止の位置 | **推測して区間を捏造しない** |

装備・コンディションは時間に紐づかないため、移行中セッションにも従来どおり適用する。

画面には次を表示する。

> アプリの更新をまたいだので、ここまでの時間にはアイテムの倍率が付きません。
> 学習時間はそのまま記録されます。

**データを失わず、根拠の無い区間にだけ追加倍率を付けない**という安全側の扱いである。

### 移行中セッションの受入条件(Q14の条件)

更新を利用して未学習の時間にBPを付けられないよう、次を守る。

| # | 条件 |
|---|---|
| 1 | 明示的な再開までは **`segments` フィールドを新設しない(未定義のまま)**。空配列 `[]` も書き込まない |
| 2 | 実績 C は**従来式**(`now - startTs - pausedAccum`)で保持する |
| 3 | 明示再開時に**初めて** `segments: [{ from: now, to: null }]` を作り、以後は新形式として扱う |
| 4 | 注意書きは、その旧セッションが**明示再開されるまでだけ**表示する。再開後は消す |
| 5 | **自動停止・画面復帰・再読み込みのいずれでも**、明示再開前の経過を新しい区間として数えない |

**1が最も壊しやすい。**「区間が無い」ことを表そうとして `segments: []` を保存すると、
§3 の判別式が新形式と見なし、**合計0分がCになって移行前の実績が消える。**
`segments` は**未定義のまま**にしておくこと。

#### 実装時に `[]` が混入する具体的な箇所

`sanitizeState` は `activeSession` を**フィールドごとに組み立て直している**(`js/calc.js:435-440`)。

```js
out.activeSession = {
  recordId:    parsed.activeSession.recordId,
  startTs:     parsed.activeSession.startTs,
  pausedAccum: typeof parsed.activeSession.pausedAccum === 'number' ? … : 0,
  pausedAt:    typeof parsed.activeSession.pausedAt    === 'number' ? … : null
};
```

ここに他フィールドと同じ調子で `segments: Array.isArray(…) ? … : []` と書くと、
**旧データを読み込むだけで全員が新形式に変わり、実績が0分になる。**

```js
// 誤り — 旧セッションを新形式に変えてしまう
segments: Array.isArray(parsed.activeSession.segments) ? parsed.activeSession.segments : []

// 正しい — 妥当な配列があるときだけフィールドを生やす
if (Array.isArray(parsed.activeSession.segments)) {
  out.activeSession.segments = 妥当性検証した区間の配列;
}
```

**`segments` は既定値を持たないフィールドとして扱う。**これが §9 段階1・段階4 の必須条件である。

5も要点である。アプリを開き直しただけ、あるいは §2 の自動停止が働いただけで
区間が生まれると、勉強していない時間にアイテムの倍率が乗る。
**フィールドが生まれる入口は「本人が再開を押す」の一つだけ**にする。

3条件は §7 の **T-2-19(画面復帰・再読み込み) / T-2-20(自動停止) / T-2-21(明示的な再開)** で
個別に検証する。各試験は **操作 / `segments` / 注意書き / 倍率** の4点をすべて確認する。
