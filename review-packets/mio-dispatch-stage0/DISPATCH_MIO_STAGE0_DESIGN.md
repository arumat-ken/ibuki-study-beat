## 結論

Claude アプリの **Dispatch（ベータ）** は画面上で確認できた。しかし、Codex または澪から
Dispatch の本文を直接読み書きする公式API、固定ファイル形式、ファイル名規則は確認できていない。
したがって初期実装は自動直結にせず、Ken さんが Dispatch の結果を貼る、または書き出したファイルを
澪へ読み込ませる手動経路を正規経路とする。

初期状態は必ずオフとし、読み取った原文をそのまま Gemini API へ送らない。端末内で許可リスト抽出、
伏せ字、短い事実要約を行い、画面で「何を伏せたか」を示す。Dispatch への書き戻しは、画面と音声で
送信候補を読み上げ、Ken さんが明示的に「はい」と確認した後だけ、手動で渡せる承認済みファイルを作る。

## 4. セキュリティ境界

### 4.1 機能スイッチ

- `Dispatch連携（実験）` は既定でオフ。
- オフの間はファイル選択、貼付欄、Dispatch報告処理を起動しない。
- 設定は既存設定を壊さない新しいキーで保存する。秘密情報や原文は保存しない。
- オンにするとき、外部送信の範囲を画面で説明する。

### 4.2 許可する項目（提案する澪内部形式）

これは **Dispatchの公式形式ではない**。手動搬送用の澪内部契約 `mio-dispatch-envelope/v1` の提案である。

- `status`: `completed` / `needs_review` / `failed` / `unknown`
- `safe_summary`: 伏せ字済みの短い結果
- `safe_next_action`: 伏せ字済みの次の作業
- `decision_needed`: `true` / `false`
- `occurred_at`: 分単位までの日時。不要なら省略
- `redaction_notice`: 伏せた分類と件数だけ。原文は入れない

上記以外は破棄する。未知のキーは通さない。

### 4.3 常に拒否する内容

- メール本文、健康データ、LINEのユーザーID
- 氏名、住所、電話番号、メールアドレス、連絡先
- APIキー、トークン、Cookie、認証情報
- URLのクエリ、フラグメント、署名部分
- 添付ファイル本文、自由形式の履歴、`localStorage` の値
- 許可リストにない任意フィールド

### 4.4 要約と音声

- 要約はまずローカルの決定的テンプレートで作る。事実の追加や推測をしない。
- Dispatch報告の既定音声は端末の `speechSynthesis` とする。これなら報告文をTTS目的で外部へ送らない。
- Gemini自然音声をDispatch報告に使う場合は別の明示設定とし、伏せ字済みの3文だけを送る。
- 「原文をGeminiへ送る」選択肢は設けない。
- 画面には `伏せ字処理済み（N項目）` を表示する。
- ログには成功時刻、失敗理由、入力の鮮度、伏せ字件数だけを残し、本文は残さない。

## 5. 段階別の実装案

### 段階1：読み取り専用

1. 設定画面に既定オフのスイッチを追加。
2. オンのときだけ、手動貼付またはローカルファイル選択を表示。
3. `mio-dispatch-envelope/v1` だけ受理。未知形式は会話を止めず理由を表示。
4. 許可リスト、伏せ字、3文要約をローカルで実行。
5. 画面と端末音声で報告。Dispatchへの書込みは実装しない。
6. 原文・秘密・`localStorage` の内容をGitHub、ログ、Geminiへ送らない。

### 段階2：確認後の書き戻し

1. Dispatch報告直後だけ「フィードバック受付モード」を明示的に開始。
2. 発話をローカル候補として表示し、伏せ字済みの送信文を読み上げる。
3. 「次の内容をDispatchへ送ります。よろしいですか」と確認。
4. `はい` の明示入力だけで承認。`いいえ`、無言、認識失敗、時間切れは破棄。
5. 公式の直接書込み経路が未確認の間は、承認済みファイルをローカル生成し、Ken さんがDispatchへ添付する。
6. 公式経路が後日確認できた場合だけ、同じ確認状態機械の後段に接続する。

### 段階3：任意の定期報告

- 段階2の実機確認後にのみ検討する。
- 重複ポーリングを防ぎ、最終成功、最終試行、取得データの鮮度を別表示する。
- 未読フラグの公式仕様が確認できるまでは、自動既読化しない。

## 6. 失敗しても会話を止めない状態機械

```text
disabled
  └─ user_enabled → ready
ready
  ├─ import_ok → sanitized → reported
  └─ import_error → ready + 画面に理由
reported
  └─ feedback_requested → draft
draft
  ├─ confirm_yes → approved_export
  ├─ confirm_no → discarded
  └─ silence/timeout/error → discarded
```

Dispatch処理の失敗は既存の `idle/listen/think/speak` 会話状態から分離する。Dispatchが読めない場合も、
通常の澪との会話、口、手ぶり、モデル選択、TTS休止は継続できる設計にする。

## 7. 検証計画

### 自動テスト

- 既定オフでは取込処理と外部送信関数が一度も呼ばれない。
- 許可リスト外の任意キー、メール本文、健康情報、ID、認証情報、秘密付きURLが出力に残らない。

- 書き戻し関数は `confirm_yes` 以外では一度も呼ばれない。
- 読取失敗、書出失敗、TTS失敗でも通常会話状態へ戻る。
- 既存テスト、ビルド、デスクトップ幅、主要モバイル幅に回帰がない。
